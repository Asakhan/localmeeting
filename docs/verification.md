- GPU 미사용 CPU 4스레드 경로로 한국어 샘플 전사 성공. 3.53초 파일에 약 11.22초가 걸려 CPU 대체 경로에서는 실시간 표시가 지연될 수 있다. 디스크 녹음은 계속되며 종료 후 남은 구간을 처리한다.
- 한국어 특화 모델의 짧은 발화 끝에 생성된 무시간 환각 문장을 발견. 0.08초 미만에 여러 글자가 붙는 구간을 배제한 뒤 해당 공개 샘플에서 재현되지 않음. 모든 환각이 제거된다는 의미는 아님.
- 한영 모델로 한국어 3.53초와 영어 11초 파일을 각각 인식하고 서로 다른 화자로 배정. 한 문장 안의 언어 전환 정확도를 평가한 것은 아님.
- 명시적으로 만든 개발 회의 전사로 제안/승인/미결/담당자/기한/후속 일정을 구분하는 JSON 생성과 Word 저장을 확인.
- Windows 150% 화면 배율에서 첫 창 크기 보정, 목록 폭, 설정 스크롤 확인.

초기 CUDA 준비 비용이 한 번 약 18.5초 발생했다. 이후 새 프로세스 첫 샘플은 약 1.8~2.0초, 준비된 모델에서는 다음과 같았다.

|---|---:|---:|
| 한국어 특화 모델, 동일 공개 발화를 반복한 파일 | 12.58초 | 약 1.68초 |
| 한국어 특화 모델, 재처리 | 3.53초 | 약 0.76초 |

| 한영 모델, 영어 파일 | 11.00초 | 약 1.06초 |

아래는 짧은 한국어 파일 1개를 패키징된 EXE로 처리하며 0.3초 간격으로 관찰한 표본이다. 프로세스 시작·모델 로딩을 포함한다. GPU 값은 데스크톱 등 다른 프로세스를 포함한 **GPU 전체 사용량**이다. RAM은 앱 작업 프로세스와 그 자식의 RSS 합계이며 GUI 상주분은 별도다.

| 단계 | 전체 시간 | 관찰 최대 RAM | GPU 전체 최대 사용량 | 전체 CPU 평균 환산 |

## 장애 기록: 2026-11-04 녹음 중 전사 중단 (WinError 5)

- 증상: 10:05 시작 회의에서 24분 48초(10:30:45)에 `PermissionError: [WinError 5] 액세스가 거부되었습니다: worker_status.json.<uuid>.tmp -> worker_status.json`로 전사 워커가 종료됐다. 녹음은 11:24까지 계속돼 원음 393개 조각은 모두 남았고, 전사 결과는 124개 조각까지만 저장됐다.
- 원인: GUI가 500 ms마다 `worker_status.json`·`transcript.jsonl`을 읽는다. Windows에서는 다른 프로세스가 대상 파일을 열고 있는 순간 `os.replace`가 실패한다(백신·검색 색인도 같은 현상을 일으킬 수 있음). 표시용 상태 쓰기 실패가 예외로 전파돼 전사 루프 전체가 멈췄다. 같은 PC에서 파일을 연 채 `os.replace`를 호출해 WinError 5가 재현됨을 확인했다.
- 조치: `core.replace_file`이 공유 위반을 최대 15초 동안 짧은 간격으로 재시도한다. 모든 원자적 교체 경로(`atomic_json`, 전사·교정·화자 재분리의 `transcript.jsonl`, `전체전사.txt`, 회의록 TXT/Word)에 적용했다. 실패 시 임시 파일을 지운다. `engine.event` 상태 쓰기는 실패해도 무시하며 전사를 계속한다. 녹음 중 전사 워커가 비정상 종료되면 GUI가 `results/` 체크포인트부터 최대 3회 자동 재시작한다.
- 회귀 테스트: `tests/test_file_lock.py` (읽기 핸들이 열린 상태에서 교체 대기, 시간 초과 시 임시 파일 정리, 상태 쓰기 실패 무시).

## 장애 기록: 2026-11-11 녹음 종료 후 2시간 정체·창 닫기 불가, 실시간 화자 과다

- 증상: 11:09~12:53 3인 회의. 회의 종료 후 15:00에야 화자 재검토가 끝났고(`diarization.json` seconds=7564, 이전 회의는 180~233초), 그동안 창을 닫으면 "회의 진행 중" 안내만 나오고 닫히지 않았다. 실시간 화면에는 "감지된 화자 8명"이 표시됐다(최종 재검토 결과는 3명).
- 원인 1 (정체): 녹음 종료 시 GUI가 `SetThreadExecutionState(ES_CONTINUOUS)`로 절전 방지를 해제했다. 시스템 로그(Kernel-Power 506/507)에서 12:55:53~14:53:59 Modern Standby가 확인됐고, 이 동안 화자 재검토 워커가 멈췄다.
- 원인 2 (닫기 불가): `closeEvent`가 녹음뿐 아니라 녹음 후 정리 중에도 무조건 닫기를 거부했다.
- 원인 3 (화자 8명): 실시간 화자 할당은 기존 중심과 유사도가 0.35 미만이면 새 화자를 만든다. 인원 설정이 있어도 상한이 없어 이 회의에서 14개 중심이 생겼고, 화면은 발언 1줄짜리 라벨까지 모두 셌다(참석자4 342행·3 218행·6 91행·1 60행·5 12행·7/13/14 각 1행).
- 조치: 워커 실행 중에는 녹음 뒤 정리 단계까지 시스템·디스플레이 절전 방지를 유지하고 처리 완료·중단 시 해제한다. 정리 중 창을 닫으면 확인 후 작업을 중단하고 원음·전사를 보존한다('다시 처리'로 이어서 가능). 설정의 발언 인원이 있으면 실시간 화자 중심 수를 그 인원으로 제한한다. 화면 인원은 20초·전체 발언 3% 이상 말한 화자만 세고, 실시간 추정/전체 재검토를 구분해 표시한다. 같은 실시간 데이터에서 표시 인원은 8 → 4명이 된다. 인원을 3으로 지정하면 실시간도 3명으로 제한된다.
- 회귀 테스트: `tests/test_speaker_count.py`.
